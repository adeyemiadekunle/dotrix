# Solo release: Phase 1 feature audit

**Audit date:** 2026-11-08

**Baseline:** `stage` after PR #229.
**Purpose:** decide what supports a solo beta, what needs work, and what to defer. This is a product assessment, not proof of deployment or an instruction to delete data.

## Evidence and limits

- Reviewed the solo direction and existing journey checklist, the web screens and navigation, and the agent tool catalog. File links below identify the implementation inspected; they do not establish runtime reliability.
- Local Anthropic observations from 2026-11-05: Home opened Tasks; task Type and Knowledge folder controls opened; Standard and fx produced read-only specialist responses; a queued follow-up ran; Stop showed `Stopped`. Nova initially failed to identify Lyra by name. Lyra reported `code_read` unavailable, while Nova read the README. A task displayed a PR and Juno review link that a separate conversation could not verify. Steering was submitted, but its effect was not confirmed.
- These observations were made against the then-local build and one disposable project, not a fresh test of this audit's stage baseline. No new production, multi-provider, browser-accessibility or live end-to-end tests were run for this audit.
- Follow-up in this worktree: the project specialist runner used the cross-project read-only filter, which removed `code.read` and `graph.read`. A candidate change retains only reads already granted by the specialist's contract; cross-project restrictions stay unchanged. Nova's Standard and fx prompts also receive specialist names and delegation handles, with the fx directory pinned in new run snapshots. Focused tests and a scheduler-level code-read regression pass. Windows fx initialization required Node's experimental WebAssembly JSPI flag; with that flag applied only to the test process, recovery, approval/resume and earlier-binding tests pass. Live provider verification and target-deployment validation remain open.
- [Product direction todo](product-direction-todo.md) describes implemented J01–J08 journeys and their test evidence; deployment and live verification remain separate. [CLAUDE.md](../CLAUDE.md) remains authoritative for production, security and engineering rules.

## Decision key

- **Keep:** retain in the supported solo journey; verify it before release.
- **Revamp:** necessary but needs a focused usability or reliability change.
- **Hide/defer:** do not lead the solo experience with it; preserve existing data, authorization and routes as appropriate.
- **Remove candidate:** consider retirement only after usage, dependencies, migration and accessibility are assessed. No destructive removal is approved by this audit.

Priority **P0** means a beta release gate; **P1** means important for the first experience; **P2** means later or evidence-dependent. These priorities do not override the production/security P0 list in CLAUDE.md.

## Ordered work after this audit

1. **Establish a reproducible baseline:** record exact commit, supported local and deployment configuration, provider/repository setup, and current browser test coverage. Confirm previous observations on current stage.
2. **Fix the blockers:** specialist identity and authorized repository tools; composer Stop/send/queue/steer; then a fresh, approval-gated Nova → Kai → Juno run with evidence returned to the original chat. Keep each fix separately reviewable.
3. **Make first use understandable:** simplify personal onboarding and Home/navigation; exercise idea, new-codebase and connected-repository paths including interrupted setup and deferred keys.
4. **Make costs and recovery visible:** verify model selection and actual usage, missing usage, provider failures and sandbox checks. Compare routine and important tasks before selecting defaults.
5. **Run beta readiness checks:** verify the supported deployment, isolation, permissions, recovery, onboarding and real GitHub/provider flows; record limitations and support instructions.
6. **Validate with solo developers:** observe task completion, confusing steps, cost and return usage. Use evidence to make the remaining hide/remove decisions and plan collaboration later.

## Decisions requiring product review

- Which providers, coding engines and deployment configurations are supported in the first beta?
- Should personal onboarding create/select the existing workspace automatically, and how should it handle a previously saved organisation choice or an invitation?
- Which task fields, navigation entries and settings should be hidden by default after testing with solo users?
- What is the minimum useful usage/cost display when a provider does not return complete data?
- Which existing features can safely be retired after dependency, migration and usage review? No item above is approved for destructive removal.
