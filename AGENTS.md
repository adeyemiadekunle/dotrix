# AGENTS.md

Read [CLAUDE.md](CLAUDE.md) before any change: it has the repo map, commands, rules, conventions, implementation status, and detailed product direction. Keep this file's summary aligned with it when those decisions change.

## Product direction

- Serve solo developers and organisation teams through one account and personal/organisation workspaces. Support three starting intentions: Explore an idea, Start a new codebase, Connect an existing repository.
- Use the [delivered product journeys](docs/product.md#delivered-product-journeys) and release checklist, with the P0 production requirements in CLAUDE.md first. J01–J08 are implemented; verify existing behaviour before planning new work. J01 shares first/subsequent New project setup and preserves invitation/auth return paths. J02 adds the three starting intentions; J03 implements the new-repository-to-reviewed-PR journey, including fresh base-branch admission and both chat runtimes. J04 adds a human-reviewed existing-repository baseline. J05 implements explicit publication, shared document/task relationships, versioned decision supersession and shared coding evidence. J06 implements reviewed, bounded GitHub Issues imports; J07 adds saved project readiness and next-action guidance. J08 adds the optional first workspace choice and labelled onboarding stepper. Deployment verification remains separate. Invited members join their intended project instead of creating an unrelated one.
- An idea can start as a lightweight draft project. GitHub is optional until needed for code; personal model setup is optional until the person uses agents. Preserve private conversations, explicit publication of shared outcomes, personal BYOK, Nova–Kai links and human merge decisions.

For the first release, follow [the solo-first product direction](docs/product.md): prioritize a reliable individual developer journey, simplify onboarding, and defer team-facing release scope while preserving workspace isolation and existing data.

## Chat and Coding direction

- Follow [the coding workspace plan](plans/046-coding-workspaces.md) for repo-first Code sessions, durable cloud workspace state and managed local worktrees. Keep approvals and issue-linked entry points in the existing Kai flow. Code accepts a repository and prompt with an optional issue. Cloud execution and session continuation check the connected repository against the admitted source. New managed local sessions stay with their original runner and retain their worktree across follow-ups.

- Dotrix owns the built-in identities: Nova coordinates the thinking specialists, and Kai is the coding agent. Chat and coding sessions are separate, linked areas.
- **Code** sits in the sidebar directly below **Chat** (`/w/{ws}/codes`). Each has its own session list; a chat links to a coding session it started (a card with "Open in Code") and receives its outcome. The side panel (Changes, Files, Terminal, Review, opened from the session header) is in Code only.
- People only ever see Kai, never the engine: not in steps, failures, errors, commits or PR bodies. The engine is recorded on the run, in the audit log and in the worker's log. A new session picks a model; the engine follows it (the person's preferred engine in Settings where it can run the model, else the provider's own, else OpenCode).
- An explicit coding request goes from Nova through a structured, permission-checked handoff to Kai. The initial chat handoff creates an approval notification; the person approves and starts Kai in Inbox, in Manual and Accept edits alike (Nova wrote the brief, so the person reads it first). Only a conversation in Auto starts Kai at once, with the requester recorded as approver, within the workspace's cap and the person's own limits (2026-11-09). Assigning Kai through Nova must create this same linked handoff. Keep the origin and results linked, preserve the person's privacy and approval mode, and return the outcome and Juno's review to Nova when available.
- Shared tasks expose only published PR/commit metadata, current-commit CI and already-posted GitHub review links through `coding/issues/{key}/outcomes`. Coding briefs, summaries, diagnostics, events, usage and Chat/Juno references stay private. Only the requester gets an optional link to their own coding session. Unpublished follow-ups do not replace published evidence; old-commit checks remain unconfirmed. A merged PR does not close a task: a person confirms completion.

- Support runtime choice behind Dotrix-owned boundaries: DeepAgents remains the default chat runner, with fx as a per-conversation choice (Nova in every work mode, the usual approvals, journaled and recoverable; no switch); on either runtime Nova delegates to specialists through the scheduler, with no switch. Kai runs Claude Code, Codex and OpenCode through headless CLI adapters, or fx over ACP, each pinned in the coding image; a session keeps its engine and model. fx chat and fx coding reach Anthropic only through its OpenAI-compatible endpoint.
- Native local runners support Claude Code, Codex and OpenCode with the authenticated desktop Browser pane. Native Claude Code 2.1.296 can run shell commands inside the shared Linux namespace with a personal Anthropic API key; subscription/OAuth and unsupported hosts keep file-only execution. Native fx requires exactly 0.0.17, Linux Bubblewrap with working user/network namespaces and a custom Chat Completions API-key profile: shell/files run in an isolated worktree, while a host relay owns model/browser credentials and direct networking is blocked. Unsupported hosts and OAuth profiles fail closed. Codex uses its workspace-write OS sandbox. Windows and live Docker Sandboxes validation remain open.
- Delegation guidance maps specialist names to their handles. Read-only project specialists retain repository and graph reads only where their contracts permit them; cross-project restrictions and existing fx run bindings stay unchanged.
- Dotrix owns delegation, workspaces, model policy, permissions, approvals, leases, audit, and recovery. A runtime and its subagents must not bypass those controls. Use per-agent or task model tiers only through host-authorized policy.
- Project settings expose the shared specialist model (no project token budget; an agent's contract may set `budget_tokens` per run). Scheduled specialists pin the applicable personal, agent, specialist, or conversation/project model at submission; the requester must still supply the provider key. The opt-in automatic routing policy uses the conversation/project model for architecture, reviews and project-changing tasks, and the specialist model for routine work; explicit personal/agent models win. Dotrix uses personal BYOK: do not introduce platform LLM budgets.
- fx chat shares the project context, layered guidance and skill catalog with DeepAgents. Its document, board, graph, connected-code and configured web tools recheck the runtime binding, current rights and lease; its changes (`agents/fx_tools.py`) go through the same approval rules as DeepAgents and run at most once per call, even across a crash. Pin its project and connected-code context encrypted per run for durable recovery; runtime changes must fail closed.
- The optional specialist-continuity preview keeps completed read-only briefs and findings private to the same person, project, conversation, and role. Each task keeps its own checkpoint; preserve scoped access and serialize tasks that share a specialist session.
- Project Chat has host-owned steering and queued follow-ups for DeepAgents and fx. Reauthorize delivery, preserve ordering and retry IDs, keep approvals unchanged, and cancel pending inputs on Stop. Accepted steering is not proof the model acted on it. Wait for continuation only on resumable runtimes, and reconcile restored checkpoint messages before rejecting steering on failure.
- Reauthorize saved specialist content and dependency provenance when it is read or executed. Keep task status visible with unavailable details redacted. Continuations reserve their specialist session under the scheduler's project lock; a busy automatic continuation remains pending.



## Runtime and OS support (2026-11-15)

Use the [current support matrix in CLAUDE.md](CLAUDE.md#runtime-and-platform-support-current-2026-11-15) as the authoritative status; older backlog entries are historical. No engine is fully verified across cloud, local CLI and packaged desktop on Windows, macOS and Linux. Source implementation, scripted real-binary tests, paid-model tests and released/deployed verification are separate evidence levels. Recent namespace adapters and the fx coding-image pin are working-tree changes, not a deployed release.

| Runtime | Nova chat | Kai cloud coding | Local native coding |
| --- | --- | --- | --- |
| DeepAgents | Default, server-side | Handoff to Kai | Not a local coding CLI |
| Claude Code | Not a Nova runtime | Implemented; image source 2.1.323, deployment/provider checks remain | Linux 2.1.296 API-key shell namespace; otherwise file/browser tools. Windows/macOS native shell not implemented. |
| Codex | Not a Nova runtime | Implemented; image source 0.169.0, deployment checks remain | 0.169.0+ native workspace-write shell adapter; Linux real-binary evidence, Windows/macOS real-machine checks pending. |
| OpenCode | Not a Nova runtime | Implemented; image source 2.3.0, including NVIDIA adapter; live cloud NVIDIA checks pending | File/browser only on native paths; commands require local `sbx`. Windows/macOS behavior is not real-machine verified. |
| fx | Optional server-side libfx **0.0.16**; compatibility/quality/recovery gaps remain | CLI/ACP **0.0.17** source pin; new cloud image not rebuilt/deployed here | Exact 0.0.17 Linux namespace + custom API-key profile. Windows/macOS and OAuth/gateway execution unsupported; no `sbx` template. |

- Cloud requests from Windows/macOS/Linux execute on the remote supported Linux sandbox. Chat clients use the server's DeepAgents/libfx runtime, not their installed coding CLI. Web/CLI/desktop availability is separate from execution support.
- Local `sbx` adapters exist for Claude Code, Codex and OpenCode; real compatible-host/template/sign-in validation remains open. `sbx` guests cannot currently reach the desktop Browser pane. Do not infer upstream OS availability or tested isolation from these adapters.
- Linux Claude/fx namespaces require working Bubblewrap user/network namespaces and system Python/Bash/Git. They isolate the runtime and shell, protect host credentials with a fixed-endpoint relay, pin the model and use private Git metadata. No unconfined fallback. Local Plan mode and applying cloud environment profiles to native runs are unsupported.
- Only **Windows x64** desktop/standalone CLI release builds are configured; they are unsigned and real-machine end-to-end validation remains open. macOS/Linux desktop installers and release pipelines are not implemented. Source development/CLI tests do not establish packaged desktop support.
- Seven Claude and twelve fx/cloud-driver namespace cases passed with scripted providers; native fx also passed a real NVIDIA fix/test. Actual new-path Electron controls, Windows/macOS native runs, live `sbx`, deployed NVIDIA cloud coding/browser tests, current-image gVisor validation and OpenShell gateway verification remain open. Nova's chat compatibility/recovery checks remain separate from coding CLI upgrades.
