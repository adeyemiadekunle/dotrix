# Plan 046 — Cloud and local coding workspaces

A person should be able to open Code, choose where Kai works, review the changes and publish through the existing approval flow. A product workspace owns the project, access, and audit history. A coding workspace is the checkout and working state of one session.

## Baseline before phases 1–2

- Code already opens issue-linked cloud and local sessions. Both the run and session currently require an issue. The web composer, CLI claim protocol, notices, and published issue outcomes depend on that relationship.
- Cloud workers export a repository checkout into the sandbox at `/sandbox/repo`. The session can reuse a warm or sleeping sandbox, and supported engines can restore a transcript. An approved environment revision controls the image, setup, and verification. Cold restoration of a transcript gives conversation continuity. Unpublished files require a separate checkpoint.
- The local runner fetches the remote branch and creates a detached worktree per attempt. Desktop can inspect it, and the runner returns a patch. Local setup and retention are separate from cloud environment setup.
- The reference workflows are [Codex Cloud](https://learn.chatgpt.com/docs/cloud), [managed worktrees](https://learn.chatgpt.com/docs/environments/git-worktrees), and [local environments](https://learn.chatgpt.com/docs/environments/local-environment).

## Delivery order

1. **Bind cloud execution to the admitted source.** Reject execution when the connected repository name differs from the name recorded on the run, and prevent a continuation from silently switching repositories. Preserve the original PR base while continuing that PR. The current name check also blocks renamed repositories. Add stable GitHub repository IDs when implementing repo-first admission so same-repository renames can be handled deliberately.
2. **Start from a repository and prompt.** Extend Code and the project coding API. Start with the project's connected repository, a validated branch, and a selected Cloud or Local worktree location. Persist source repository ID, base branch, and starting commit. Allow a nullable issue reference, migrate existing rows without changing their links, and use a standalone session title and prompt where there is no issue. Audit session listing, notifications, runner claims, review, activity and issue outcomes for nullable issue references. Reuse Kai's existing model choice, permissions, approvals, and publication. Keep Nova and issue entry points. Verify a cloud prompt reaches diff, approval and a PR against the chosen branch with no issue created.
3. **Keep a local worktree per session.** Bind a session to an eligible runner, repository and managed worktree. Keep one writer under a turn lease. Add Open in IDE, Create branch, explicit cleanup and restoration from a verified snapshot. Add local OS-specific setup and app actions through the supported runner boundaries. Test desktop restart, retry, dirty checkout protection, concurrent sessions, and recovery after cleanup. Validate packaged OS support before advertising it.

   Desktop Files can open a worktree in VS Code or VS Code Insiders and create a local branch in an idle managed worktree. Branch creation keeps the worktree edits for manual work.

4. **Restore the cloud workspace after sandbox loss.** Persist bounded Git changes independently of the sandbox, with repository and base identity, artifact integrity, and a transcript reference where supported. Recreate using the admitted environment, then restore changes against their recorded base. Retain the checkpoint if restore detects drift or corruption. Keep ignored files, credentials and process state out of the checkpoint. Verify that eviction and worker restart recover unpublished files and produce the same review diff. Add environment verification and consider dependency caching after measuring cold setup.

   Phase 4 now checkpoints in-progress cloud Build turns and restores the latest valid patch when retrying the same turn from the same base. Verification against a real cloud provider, environment verification, and dependency caching remain open.

5. **Move changes across environments, then start without a repository.** Transfer a reviewed, versioned changeset into a new managed worktree after checking the base and showing conflicts. Add the reverse flow with an upload preview and explicit authorization. Add private repository-free cloud workspaces once cloud recovery is proven, with explicit export or publication. Verify a dirty checkout is preserved and existing PRs are not duplicated.

Phases 1–2 and the managed-worktree runner binding and reuse portion of phase 3 are implemented. Compatible runners keep the same worktree across follow-ups and protect unpublished files from replacement and age-based cleanup. Phase 3 also includes explicit local CLI snapshot and restore. Snapshots use the linked checkout's Git object store and restore the saved files into a missing managed worktree against the saved base. A restored worktree stages its recovered changes for inspection. Explicit CLI cleanup saves a separate recovery point before removing a clean, idle worktree. Packaged platform validation, handoff and repository-free coding remain open. Validate production sandbox behavior on stage before enabling new cloud paths by default.
